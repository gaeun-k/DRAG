# 테디노트 RAG 코드 상세 해설

이 해설은 질문 본문에 있는 8단계 PDF RAG 코드와 **사용자가 첨부한 노트북 JSON 7개**를 기준으로 합니다. GitHub의 현재 파일과 첨부 버전이 동일하다고 가정하지 않습니다. 첨부 파일은 코드 셀만 `references/attachment_1.py.txt`부터 `attachment_7.py.txt`까지 추출했습니다. `# Cell N`은 markdown 셀을 포함하여 센 **1부터 시작하는 원래 셀 위치**입니다. 참고 파일은 실행용 스크립트가 아니므로 위에서부터 일괄 실행하지 마세요.

기반 저장소는 [teddylee777/langchain-kr의 12-RAG](https://github.com/teddylee777/langchain-kr/tree/main/12-RAG)입니다. 아래의 세부 분석은 제공된 코드에 대한 설명입니다.

## 1. 전체 예제의 관계

| 대상 | 주제 | 무엇을 배우는가 | 2주차에서의 위치 |
| --- | --- | --- | --- |
| 질문 본문의 첫 코드 | PDF 기본 RAG | 8단계 전체 흐름 | 필수 |
| 첨부 1 | RAG 기본 구조 / 네이버 뉴스 QA | 웹 문서를 검색하고 한국어 답변 생성 | 필수 |
| 첨부 2 | LangChain의 RAG 파헤치기 | 로더·분할기·임베딩·검색기 교체 실험 | 핵심 부분 우선 |
| 첨부 3 | 이전 대화를 기억하는 Chain | 세션별 대화 이력 주입 | 선택 심화 |
| 첨부 4 | 웹 문서 RAPTOR | 문서를 계층적으로 묶고 요약 | 심화 |
| 첨부 5 | PDF RAPTOR | 같은 알고리즘을 보고서에 적용 | 심화 |
| 첨부 6 | Chain of Density | 정보 밀도를 높이는 반복 요약 | 별도 요약 기법 |
| 첨부 7 | 멀티모달 RAG | 텍스트·표·이미지를 함께 검색 | 심화 |

2주차 목표를 만족하려면 첫 코드와 첨부 1의 흐름을 이해하고, 첨부 2의 분할·검색 실험을 해보면 됩니다. RAPTOR와 이미지 처리를 모두 구현해야 하는 과제는 아닙니다.

## 2. 첫 번째 PDF 코드: import부터 실행까지

### 2.1 각 import가 맡는 일

| 이름 | 역할 | 입력 → 출력 |
| --- | --- | --- |
| `PyMuPDFLoader` | PDF의 텍스트와 페이지 정보 읽기 | 파일 경로 → `list[Document]` |
| `RecursiveCharacterTextSplitter` | 큰 본문을 작은 청크로 분할 | 문서 목록 → 청크 문서 목록 |
| `OpenAIEmbeddings` | 검색에 쓸 숫자 벡터 생성 | 텍스트 → 실수 벡터 |
| `FAISS` | 벡터 저장과 가까운 벡터 검색 | 문서·임베딩 → 벡터스토어 |
| `PromptTemplate` | 검색 근거와 질문을 지정한 문장 틀에 삽입 | 변수 딕셔너리 → 프롬프트 |
| `RunnablePassthrough` | 들어온 값을 그대로 다음 단계에 전달 | 질문 문자열 → 같은 문자열 |
| `ChatOpenAI` | 프롬프트를 받아 답변 생성 | 메시지/프롬프트 → `AIMessage` |
| `StrOutputParser` | 모델 응답에서 문자열 출력 추출 | 모델 응답 → `str` |

`Document`는 보통 `page_content`와 `metadata`를 가집니다. `page_content`는 실제 검색·생성에 사용할 본문이고, `metadata`에는 파일명·페이지·URL 같은 출처가 들어갑니다. `docs`의 개수는 로더 정책에 따른 개수이므로 항상 파일 개수와 같지는 않습니다.

### 2.2 1단계: 문서 로드

```python
loader = PyMuPDFLoader("data/SPRI_AI_Brief_2023년12월호_F.pdf")
docs = loader.load()
```

첫 줄은 파일을 어떻게 읽을지 설정합니다. 실제로 파일을 읽는 것은 `load()`입니다. 일반적인 페이지 모드에서는 페이지별 Document가 만들어집니다. 이 단계는 모델을 훈련하거나 답변을 만드는 단계가 아닙니다.

상대 경로는 실행한 작업 디렉터리 기준입니다. PDF 파일이 제공되지 않거나 현재 폴더가 다르면 실패합니다. 스캔 이미지뿐인 PDF는 일반 텍스트 추출만으로 읽히지 않습니다. 이번 앱은 별도의 원본 PDF 없이 실행되도록 자체 위키와 업로드 입력을 제공합니다.

### 2.3 2단계: 청킹

```python
text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=50)
split_documents = text_splitter.split_documents(docs)
```

기본 길이 함수가 `len`이면 1000은 **문자 수**입니다. 1000토큰이나 1000단어가 아닙니다. 재귀 분할은 큰 구분자로 먼저 나누고 너무 긴 조각을 더 작은 구분자로 다시 나눕니다. 겹침 50은 경계에서 문맥을 유지하려는 목표값으로, 구분자와 병합 결과에 따라 모든 청크가 정확히 50자를 공유하지는 않습니다. [분할기 공식 설명](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter).

작은 청크는 특정 사실을 찾기 쉽지만 설명이 끊길 수 있습니다. 큰 청크는 문맥이 풍부하지만 서로 다른 주제가 섞입니다. 겹침을 늘리면 경계 문맥은 더 남지만 중복 임베딩과 입력량이 증가할 수 있습니다. 이번 앱은 크기 1000, 겹침 100을 시작점으로 두고 바꿔 실험할 수 있게 했습니다.

### 2.4 3단계: 임베딩 객체

```python
embeddings = OpenAIEmbeddings()
```

임베딩 API를 호출할 설정 객체입니다. 여기서 `split_documents`를 넘기지 않았으므로 이 줄만으로 청크 전체가 벡터화되는 것은 아닙니다. 실제 문서 임베딩은 다음 `FAISS.from_documents` 내부에서 요청됩니다. 질문할 때도 질문 문자열을 같은 임베딩 체계로 바꾸어 검색합니다.

임베딩 모델은 답변 문장을 작성하지 않습니다. 이번 앱은 임베딩 이름을 `text-embedding-3-small`로 명시했습니다. 답변 모델 `gpt-4.1-mini`와는 별개의 모델입니다. [OpenAI 임베딩 모델](https://developers.openai.com/api/docs/models/text-embedding-3-small), [답변 모델](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

### 2.5 4단계: 벡터스토어 생성

```python
vectorstore = FAISS.from_documents(documents=split_documents, embedding=embeddings)
```

각 청크의 본문을 임베딩하고, 숫자 벡터의 검색 인덱스와 대응하는 문서를 관리할 저장소를 만듭니다. 검색 결과에서 원문을 되돌려주려면 벡터뿐 아니라 문서와의 연결도 필요합니다.

주석에 “DB 생성 및 저장”이라고 쓰여 있어도 이 한 줄이 디스크 파일까지 저장하는 것은 아닙니다. 별도 `save_local()` 같은 작업이 없으면 프로세스 메모리에서 사용하는 저장소입니다. FAISS 인덱스 생성은 LLM 파인튜닝도 아닙니다.

### 2.6 5단계: Retriever

```python
retriever = vectorstore.as_retriever()
```

FAISS를 LangChain 실행 흐름에서 사용할 검색기 인터페이스로 감쌉니다. 검색은 나중에 `retriever.invoke(question)` 혹은 체인 실행 때 수행됩니다. 검색기는 **문서 목록**을 반환하며 스스로 최종 답변을 생성하지 않습니다. 결과 개수는 `search_kwargs={"k": 4}`처럼 명시하면 실험이 쉬워집니다.

`top-k`는 가장 가까운 문서를 고르는 방식이지 “정답 문서가 존재함”을 보증하는 방식이 아닙니다. 아무 관련 없는 질문에도 상대적으로 가까운 자료는 나올 수 있습니다.

### 2.7 6단계: 프롬프트

`PromptTemplate.from_template(...)`의 `{context}`에는 검색된 정보, `{question}`에는 사용자의 질문이 들어갑니다. “모르면 모른다고 말하라”, “한국어로 답하라”는 생성 규칙입니다. 문자열 템플릿을 만드는 것만으로 LLM 호출은 발생하지 않습니다.

첫 코드에는 `format_docs`가 없습니다. 검색 결과 `list[Document]`가 템플릿에서 객체 표현 형태로 문자열화될 수 있습니다. 교육상 동작을 이해하는 데는 도움이 되지만, 실제 앱에서는 본문과 출처를 명시적으로 조합하는 편이 읽기 쉽습니다. 이번 앱은 `[1] 파일명, 페이지`와 본문을 함께 넣어 화면의 근거 번호와 연결합니다.

### 2.8 7단계: 언어모델

```python
llm = ChatOpenAI(model_name="gpt-4.1-mini", temperature=0)
```

모델 설정입니다. `temperature=0`은 출력의 무작위성을 줄이는 설정이지 정확성이나 완전한 재현성을 보장하는 장치는 아닙니다. API 키와 네트워크, 모델 접근 권한이 필요합니다. 이번 앱에서는 `model=` 인자를 사용하고 timeout과 재시도 횟수를 제한했습니다.

### 2.9 8단계: LCEL 체인

```python
chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
```

`|`는 앞 단계 출력을 다음 단계 입력으로 넘기는 LCEL 연결입니다. 질문 문자열 하나가 첫 딕셔너리의 두 경로에 전달됩니다.

```text
"삼성 가우스란?"
 ├─ retriever → [Document(...), Document(...)] → context
 └─ RunnablePassthrough → "삼성 가우스란?"       → question
                  ↓
       {context: ..., question: ...}
                  ↓ prompt
            완성된 프롬프트
                  ↓ llm
               AIMessage
                  ↓ StrOutputParser
               답변 문자열
```

따라서 `RunnablePassthrough`는 대화 기억 기능이 아닙니다. 그리고 **체인 정의만으로 질문은 실행되지 않습니다.** 다음처럼 호출해야 합니다.

```python
answer = chain.invoke("삼성 가우스에 대해 설명해 주세요.")
print(answer)
```

`.stream(question)`은 출력 조각을 순차적으로 받는 반복자를 반환합니다. 반복자를 변수에 넣기만 하고 순회하지 않으면 출력 소비가 이루어지지 않습니다. `StrOutputParser`는 답변 사실 확인이나 출처 검증기가 아닙니다.

## 3. 첨부 1: 네이버 뉴스 기반 기본 QA

참고 코드: `references/attachment_1.py.txt`.

### 환경 설정

`load_dotenv()`는 `.env` 설정을 환경변수로 읽습니다. 키를 발급해 주지는 않습니다. `logging.langsmith("CH12-RAG")`는 실행 추적을 위한 설정입니다. 검색 필수 기능이 아니며, 추적을 쓰면 프롬프트·출력 등 기록되는 데이터의 범위를 확인해야 합니다. 이번 앱은 LangSmith 설정을 추가하지 않았습니다.

### 웹 페이지 수집

`WebBaseLoader(web_paths=(url,), bs_kwargs=...)`는 URL의 HTML에서 텍스트를 수집합니다. `SoupStrainer`는 지정한 HTML 요소만 파싱하도록 범위를 좁힙니다. 예제는 뉴스 제목과 기사 본문 영역을 선택합니다. 메뉴나 광고가 섞이는 것을 줄이려는 목적입니다.

CSS 클래스가 바뀌거나 로그인이 필요한 페이지라면 결과가 비거나 잘못될 수 있습니다. 네이버용 선택자를 다른 블로그에 그대로 사용하면 안 됩니다. 로드 직후 `docs[0].page_content`를 확인하는 이유가 이것입니다.

### 분할·인덱싱·생성

크기 1000, 겹침 100으로 분할하고 FAISS에 저장합니다. 설명 글에 Chroma가 언급되어 있지만 **제공된 실제 실행 코드는 FAISS**를 사용합니다. `from langchain import hub`를 import하더라도 `hub.pull`이 주석이면 허브 프롬프트를 가져오지 않습니다. 실제 사용하는 것은 직접 만든 한국어 프롬프트입니다.

`rag_chain.stream(...)`과 `stream_response(answer)`는 스트리밍 출력을 보여줍니다. `stream_response`는 테디노트 편의 함수이며 검색 알고리즘이 아닙니다. 지원금 액수 질문 셀처럼 `.stream(...)`을 변수에 넣고 바로 출력 함수를 호출하지 않는 부분은 노트북에 자동으로 답이 표시된다고 기대해서는 안 됩니다.

마지막 임직원 수 질문은 기사에 정보가 없는 경우의 응답을 확인하는 데 쓸 수 있습니다. 다만 그 기사 본문에 정보가 실제로 있는지 먼저 확인해야 하며, “모른다”는 답을 지시했다고 환각이 완전히 사라지는 것은 아닙니다.

## 4. 첨부 2: RAG 구성요소를 하나씩 바꿔보기

참고 코드: `references/attachment_2.py.txt`. 여러 독립 실험을 한 노트북에 모았기 때문에 `docs`, `splits`, `vectorstore`가 중간에 덮어써집니다.

### 4.1 로더 비교 — 셀 16~29

| 로더 | 읽는 자료 | 확인할 점 |
| --- | --- | --- |
| `WebBaseLoader` | 뉴스·웹 HTML | 본문 선택자, 사이트 구조 변화 |
| `PyPDFLoader` | PDF의 텍스트 | 페이지 번호, 텍스트 추출 순서 |
| `CSVLoader` | CSV 행 | 한 행을 문서로 보는 방식, 인코딩 |
| `TextLoader` | TXT | UTF-8 등 인코딩 |
| `DirectoryLoader` | glob과 일치하는 여러 파일 | 실제로 선택된 파일, loader_cls |
| `PythonLoader` | Python 소스 | 코드 문자열 자체를 문서로 읽음 |

`DirectoryLoader(".", glob="**/*.py", loader_cls=PythonLoader)`는 폴더 아래 Python 파일을 찾고 각 파일을 PythonLoader로 읽습니다. Python 소스를 실행하는 것이 아닙니다. 기본 로더에 의존하면 별도 파싱 패키지가 필요할 수 있습니다.

`docs[10]`은 0부터 세므로 **11번째 문서**입니다. PDF에서는 보통 11번째 페이지에 대응하지만 CSV에서는 행 문서입니다. 일부 주석의 “10번째 페이지”는 인덱스나 자료 형태와 맞지 않습니다. `docs[0]`을 출력하면서 “10번째 페이지”라고 적은 주석도 있습니다.

### 4.2 분할기 비교 — 셀 35~57

`CharacterTextSplitter`는 하나의 구분자(`\n\n`, `\n`, 공백 등)를 중심으로 나눕니다. 구분자가 없는 긴 덩어리에서는 지정한 크기를 초과하는 조각이 남을 수 있습니다. `RecursiveCharacterTextSplitter`는 여러 구분자를 순차적으로 적용하여 더 작은 단위로 내려갑니다.

`split_text(text)`는 문자열 목록을 반환합니다. `split_documents(docs)`는 메타데이터를 가진 Document 목록을 반환합니다. 출처를 보여줄 RAG에서는 후자가 편리합니다.

`loader.load_and_split(text_splitter=...)`는 읽기와 분할을 묶습니다. 셀 44에서는 결과를 `split_docs`에 담고도 출력은 기존 `docs`로 확인하고 있어 새 분할 결과를 확인한 것이 아닙니다. `split_docs`를 출력해야 합니다.

`SemanticChunker(OpenAIEmbeddings(), add_start_index=True)`는 의미 차이를 이용해 분할 경계를 정하는 실험입니다. 분할 단계부터 임베딩 비용과 시간이 들 수 있습니다. 문자 기준 분할보다 무조건 좋다는 뜻은 아니며, 2주차에서는 기본 분할을 먼저 이해하는 편이 좋습니다.

### 4.3 임베딩과 벡터스토어 — 셀 60~70

`OpenAIEmbeddings`는 외부 API, `HuggingFaceBgeEmbeddings`와 `FastEmbedEmbeddings`는 다른 임베딩 실행 경로를 보여줍니다. 오픈소스 모델 사용에는 로컬 설치·모델 다운로드·메모리·CPU/GPU 시간이 필요합니다. API가 없다고 실행 비용이 전혀 없는 것은 아닙니다.

임베딩 모델을 바꾸면 같은 문서라도 벡터 공간이나 차원이 달라질 수 있으므로 인덱스를 다시 만들어야 합니다. 문서 임베딩과 질문 임베딩은 호환되는 동일한 설정을 사용해야 합니다.

FAISS와 Chroma는 임베딩을 검색하는 저장 계층을 교체하는 예입니다. `from_documents`를 다시 실행할 때 OpenAI 임베딩을 사용하면 같은 본문을 반복 전송할 수 있습니다.

### 4.4 검색 전략 — 셀 73~89

| 방식 | 동작 | 기대 효과 / 한계 |
| --- | --- | --- |
| `similarity` | 질문과 가까운 청크 선택 | 단순하지만 비슷한 청크가 중복될 수 있음 |
| `similarity_score_threshold` | 점수가 기준을 넘는 청크만 선택 | 자료가 없으면 빈 결과 가능, 기준 보정 필요 |
| `mmr` | 질문 관련성과 결과 간 다양성을 함께 고려 | 비슷한 내용만 반복되는 것을 줄임 |
| `MultiQueryRetriever` | LLM이 여러 검색 질문을 만들고 결과 통합 | 표현 차이를 보완하나 추가 호출과 지연 발생 |
| `BM25Retriever` | 단어 일치와 빈도 기반 검색 | 고유명사에 유용, 한국어 토큰화에 민감 |
| `EnsembleRetriever` | 여러 검색 결과의 순위를 결합 | 키워드와 의미 검색을 보완 |

`score_threshold=0.8`은 “정답일 확률 80%”가 아닙니다. 점수 정의와 정규화는 검색 저장소 설정에 달려 있습니다. FAISS 거리값과 관련성 점수도 그대로 같은 값으로 취급하면 안 됩니다.

예제의 `weights=[0.5, 0.5]`는 두 검색기의 순위 결합 비중이지 서로 다른 점수를 단순 평균해 정확도를 계산한다는 뜻이 아닙니다. `배`가 신체·선박·과일로 쓰이는 예시는 의미 검색과 키워드 검색의 차이를 관찰하려는 장치입니다. `ships`, `pear`처럼 언어를 바꾼 질의는 사용하는 임베딩의 다국어 성능에 영향을 받습니다.

셀 81은 `query`를 만들어 놓고 `query=question`을 사용합니다. 이전 셀의 question이 들어갈 수 있으므로 의도한 질의를 넣었는지 확인해야 합니다. 구형 `get_relevant_documents`는 이번 프로젝트에서 `retriever.invoke(query)`로 통일했습니다.

### 4.5 프롬프트·모델·호출 비용 — 셀 92~101

`hub.pull("rlm/rag-prompt")`는 외부에 저장된 프롬프트를 불러옵니다. 내용과 요구 변수명을 확인해야 하며, 이름만으로 한국어 답변이 보장되지는 않습니다. 이번 앱은 외부 프롬프트 다운로드 없이 로컬에 정의합니다.

`get_openai_callback()`은 호출의 토큰 사용량·비용 정보를 관찰하는 보조 도구입니다. 모든 모델의 모든 가격이 자동으로 정확하게 반영된다고 가정하지 말고 계정 사용량과 대조해야 합니다.

`HuggingFaceHub(repo_id="google/flan-t5-xxl", ...)`는 생성 모델 공급자를 바꾸는 예입니다. 첨부에 있는 구형 클래스·모델 ID가 현재 동일한 방식으로 동작한다고 보장할 수는 없습니다. 이 과제 앱은 첨부 첫 코드의 `gpt-4.1-mini`를 유지했습니다.

### 4.6 마지막 PDF 템플릿 실험 — 셀 103 이후

PDF → 분할 → BM25와 FAISS → 앙상블 → 프롬프트 → LLM을 한데 묶습니다. 다음 부분은 그대로 복사하기 전에 고쳐야 합니다.

- `split_docs`에 PDF 결과를 넣고 첫 FAISS 생성에서는 이전 `splits`를 사용합니다. 다른 문서가 인덱싱될 수 있습니다. 이후 실제 앙상블용 FAISS는 `split_docs`로 다시 만듭니다. 잘못된 첫 생성 줄은 불필요한 호출이기도 합니다.
- PDF 로더만 새로 지정하고 `docs`를 새 PDF 목록으로 갱신하지 않아 문서 수 출력이 이전 문서 기준일 수 있습니다.
- 결과 출력의 `question`, `response`는 현재 체인으로 실행하기 전이라 앞 셀 값이거나 미정의 변수일 수 있습니다. 먼저 `rag_chain.invoke(question)`를 실행해야 합니다.
- 버전별 import 경로가 혼재합니다. 핵심 분할기·프롬프트·로더를 각각 `langchain_text_splitters`, `langchain_core`, `langchain_community`에서 가져오도록 정리할 필요가 있습니다.

새 앱은 함수에 문서를 전달하고 해당 문서에서 생성된 `self.chunks`만 인덱싱하므로 노트북 셀 간 변수 혼동을 줄였습니다.

## 5. 첨부 3: 이전 대화를 기억하는 체인

참고 코드: `references/attachment_3.py.txt`.

### 일반 대화 체인

`ChatPromptTemplate.from_messages`는 system과 human 등 역할별 메시지를 만듭니다. `MessagesPlaceholder(variable_name="chat_history")`는 과거 메시지 목록을 끼워 넣을 자리입니다. placeholder 자체가 대화를 저장하지는 않습니다.

`store = {}`는 세션 ID별 기록을 담는 딕셔너리입니다. `get_session_history(session_ids)`는 해당 ID의 기록이 없으면 `ChatMessageHistory()`를 만들고 반환합니다. 프로세스 메모리이므로 재시작하면 사라집니다.

`RunnableWithMessageHistory`는 실행 전 기록을 가져와 체인에 넣고 실행 후 새 대화를 기록하도록 감쌉니다. `input_messages_key="question"`과 `history_messages_key="chat_history"`는 입력·이력 필드와 맞아야 합니다. `chat_history`라는 이름 자체가 절대적인 예약어는 아니지만 변경하면 연결된 모든 키를 함께 바꿔야 합니다.

같은 `configurable.session_id="abc123"`로 “내 이름은 테디” 다음에 “내 이름이 뭐라고?”를 호출하면 과거 문장이 모델 입력에 포함됩니다. 다른 세션 ID는 별도의 기록입니다. 모델의 가중치가 학습되는 것이 아닙니다.

### RAG에 기록 추가

RAG 체인은 입력이 문자열 하나가 아니라 `{question: ...}` 딕셔너리입니다. `itemgetter("question")`은 그중 질문만 꺼내 검색기로 보냅니다. `itemgetter("chat_history")`는 이력을 프롬프트에 전달합니다.

```text
질문 딕셔너리
 ├─ question → 검색기 → context
 ├─ question → question
 └─ 저장된 기록 → chat_history
                     ↓
                프롬프트 → LLM
```

이 예제는 **답변 생성 시 이력을 전달하지만 검색 질의를 이력으로 재작성하지는 않습니다.** “그 모델은 누가 만들었어?”에서 검색기는 그 문장만 받습니다. 이전 답변의 대상 이름을 검색 질의에 풀어 쓰는 history-aware retrieval은 추가 단계입니다. “이전 답변을 영어로 번역”하는 예시에서도 불필요한 검색이 수행될 수 있습니다.

이번 미니 앱은 2주차 기본 구조에 맞춰 독립 질문 QA로 구현했습니다. Streamlit 대화 목록은 화면용이며 이 노트북의 RunnableWithMessageHistory 기능을 구현한 것은 아닙니다.

## 6. 첨부 4와 5: RAPTOR

참고 코드: `references/attachment_4.py.txt`, `references/attachment_5.py.txt`.

기본 RAG는 원문 조각만 검색합니다. RAPTOR 예제는 비슷한 원문을 묶어 요약하고, 그 요약들을 다시 묶어 상위 요약을 만듭니다. 세부 질문에는 원문, 넓은 질문에는 요약이 검색될 기회를 주려는 구조입니다.

```text
원문 A, 원문 B → 그룹 요약 X ┐
원문 C, 원문 D → 그룹 요약 Y ┴→ 상위 요약 Z

이 예제의 최종 검색 대상 = A, B, C, D, X, Y, Z를 합친 목록
```

### 6.1 두 예제의 입력 차이

첨부 4는 `RecursiveUrlLoader`로 LangChain 관련 웹 문서를 수집합니다. `max_depth=20`은 링크 탐색 범위를 크게 만들 수 있으며, 문서 사이트 구조에 따라 양이 달라집니다. BeautifulSoup의 `.text`로 HTML을 텍스트화합니다.

첨부 5는 `PDFPlumberLoader`로 PDF 페이지를 읽습니다. 이후 임베딩→클러스터→요약 로직은 같은 계열입니다. PDF 버전의 요약 프롬프트는 자료의 도메인에 맞춰 읽어야 합니다.

### 6.2 전처리와 모델 설정

`num_tokens_from_string`은 tiktoken 인코더로 토큰 수를 셉니다. 히스토그램은 문서 길이의 분포를 보여주는 진단용입니다. 직접적인 검색 단계가 아닙니다.

문서를 source로 정렬하고 뒤집어 결합하는 것은 입력 순서를 구성하는 방법이지 의미적으로 좋은 순서를 자동 발견하는 기법은 아닙니다. PDF 페이지가 같은 source를 가지면 역순으로 뒤집는 결과가 의도와 맞는지 확인해야 합니다.

`from_tiktoken_encoder`는 길이 판정에 토크나이저를 사용하는 분할기를 구성합니다. 첨부 4는 chunk_size=2000, 첨부 5는 100으로 `texts_split`을 만듭니다. 그러나 뒤에서 `leaf_texts = docs_texts.copy()`를 사용하므로 **만든 texts_split이 트리 입력에 사용되지 않습니다.** “설정한 청크 크기로 트리를 만들었다”고 설명하면 코드와 다릅니다.

`LocalFileStore`와 `CacheBackedEmbeddings`는 임베딩 결과를 저장하고 재사용하기 위한 장치입니다. namespace를 모델 이름으로 두면 모델 간 캐시 구분에 도움이 됩니다. 그런데 첨부의 `embed()`와 최종 FAISS 생성은 `cached_embeddings` 대신 원래 `embeddings`를 호출합니다. **캐시 객체를 생성하는 것만으로 캐시가 적용되지는 않습니다.**

### 6.3 함수별 역할

| 함수 | 하는 일 | 반환/다음 단계 |
| --- | --- | --- |
| `global_cluster_embeddings` | UMAP으로 전체 벡터 차원 축소 | 축소된 벡터 배열 |
| `local_cluster_embeddings` | 큰 그룹 안에서 다시 UMAP 적용 | 그룹 내부 축소 벡터 |
| `get_optimal_clusters` | 후보 GMM을 학습하고 BIC 비교 | 가장 낮은 BIC의 그룹 수 |
| `GMM_cluster` | 각 벡터의 그룹 소속 확률 계산 | 임계값을 넘는 그룹 ID 목록 |
| `perform_clustering` | 전역 그룹 후 지역 그룹 생성 | 각 문서에 연결된 최종 그룹 ID |
| `embed` | 본문 목록을 임베딩해 NumPy 배열로 변환 | 문서 수 × 임베딩 차원의 배열 |
| `embed_cluster_texts` | 임베딩·클러스터링 결과를 합침 | text, embd, cluster 열의 DataFrame |
| `fmt_txt` | 한 그룹의 본문을 구분자로 연결 | 요약 프롬프트용 문자열 |
| `embed_cluster_summarize_texts` | 그룹별 본문을 LLM으로 요약 | 원문 그룹 표와 요약 표 |
| `recursive_embed_cluster_summarize` | 이전 요약을 다음 층 입력으로 반복 | level별 결과 딕셔너리 |
| `format_docs` | 검색 문서를 `<document>`로 감쌈 | 최종 QA context |

UMAP은 고차원 벡터의 구조를 더 낮은 차원에 표현하려는 단계입니다. GMM은 여러 가우시안 분포를 섞어 자료를 설명합니다. 하나의 문서가 한 그룹에만 속하도록 고정하지 않고 소속 확률이 threshold를 넘는 여러 그룹에 들어갈 수 있습니다.

BIC는 모델의 적합도와 복잡도를 함께 고려하는 기준입니다. 낮은 값을 선택한다고 QA 정확도를 직접 최적화하는 것은 아닙니다. `np.arange(1, max_clusters)`는 끝값을 포함하지 않아 실제 후보는 max_clusters보다 하나 작게 끝납니다.

`perform_clustering`은 문서 수가 `dim + 1` 이하이면 하나의 그룹으로 처리합니다. 데이터가 너무 적은 상태에서 차원 축소와 클러스터링을 무리하게 하지 않으려는 분기입니다. 전역·지역 그룹 번호가 겹치지 않도록 `total_clusters`를 더합니다.

### 6.4 재귀 요약

`embed_cluster_summarize_texts`는 다중 소속을 문서-그룹 쌍으로 펼친 뒤 각 그룹을 요약합니다. 요약 표에는 summaries, level, cluster가 들어갑니다. `recursive_embed_cluster_summarize`는 최대 층수에 도달하거나 그룹이 하나가 되면 멈춥니다.

최종 `all_texts`에는 원문과 각 레벨 요약이 모두 들어갑니다. 이를 하나의 FAISS에 저장하므로 제공된 검색 구현은 **트리를 위에서 아래로 따라 내려가는 탐색이 아니라 모든 층을 평평하게 합쳐 검색하는 방식**입니다.

### 6.5 실행 시 주의할 코드 지점

- 원문 여러 개를 합친 한 그룹이 길면 요약 프롬프트가 모델 입력 한도를 넘을 수 있습니다. 층수만 제한한다고 한 번의 호출 길이가 제한되지는 않습니다.
- `RANDOM_SEED`가 정의되어 있어도 UMAP 생성에 random_state를 주지 않은 부분이 있어 전체 과정의 완전한 재현성을 보장하지 않습니다.
- FAISS 저장 폴더가 있으면 `local_index`에 병합하지만, 검색기는 계속 새 `vectorstore`로 만듭니다. 디스크의 병합 결과 전체로 검색하려면 그 객체를 사용해야 합니다.
- 같은 자료를 계속 병합하면 중복 인덱싱이 생길 수 있습니다. 원문 ID와 중복 판별 정책이 필요합니다.
- 로컬 FAISS 문서 저장에는 역직렬화가 관련됩니다. 신뢰할 수 없는 인덱스를 불러오기 위해 안전 옵션을 무작정 완화해서는 안 됩니다. 이번 앱은 외부 인덱스를 읽지 않습니다.
- `from_texts`로 문자열만 저장하면 원문의 파일명·페이지와 요약의 연결을 따로 유지하지 않는 한 출처 추적이 어렵습니다.
- 요약에서 수치나 조건이 빠질 수 있습니다. 상위 요약의 답을 원문과 확인하는 절차가 필요합니다.

짧은 자체 위키 QA에서는 이 단계들이 시간·의존성·비용을 크게 늘릴 수 있어 이번 기본 앱에는 넣지 않았습니다.

## 7. 첨부 6: Chain of Density

참고 코드: `references/attachment_6.py.txt`.

이 코드는 **검색 기반 QA 체인보다는 요약 체인**입니다. 웹 글 전체를 읽고, 제한된 길이 안에서 점점 더 많은 중요 정보를 담는 요약을 요청합니다. 벡터스토어나 retriever가 없습니다.

### 첫 번째 방식 — 셀 3~5

`WebBaseLoader`로 글을 읽고 `content = docs[0].page_content`로 본문을 꺼냅니다. `hub.pull("lawwu/chain_of_density")`로 프롬프트를 가져옵니다. `{"ARTICLE": RunnablePassthrough()}`는 본문 문자열을 ARTICLE 변수에 넣습니다.

`SimpleJsonOutputParser`는 모델이 생성한 JSON을 Python 객체로 해석합니다. 파서가 요약을 수행하는 것은 아닙니다. JSON 출력이 잘못되면 파싱 오류가 날 수 있습니다.

### 두 번째 방식 — 셀 6

프롬프트를 직접 작성해 반복마다 “이전 요약에서 빠진 1~3개 핵심 개체 찾기 → 같은 길이로 다시 쓰기”를 다섯 번 요구합니다. 인명·기업·숫자·사건 같은 정보를 더 담도록 지시하며, 이미 들어간 개체를 유지하도록 요청합니다.

중요한 점은 코드에 Python의 5회 호출 루프가 있는 것이 아니라 **한 번의 모델 호출에 5회 반복 결과를 작성하라고 지시한다는 것**입니다. 정확한 단어 수, 개체 보존, JSON 길이 5개가 자동 보장되지는 않습니다. 특히 영어식 단어 수 제약을 한국어에 적용할 때는 평가 기준을 정해야 합니다.

`StreamCallback.on_llm_new_token`은 생성 중 토큰을 출력합니다. `JsonOutputParser` 뒤의 `lambda x: x[-1]["Denser_Summary"]`는 목록의 마지막 요약만 꺼냅니다. 스트리밍 중 표시되는 원문 JSON과 최종 result는 서로 다른 출력 형태입니다.

여기서 `RunnablePassthrough`는 기사 본문을 넘기는 데 사용되고, 첫 기본 RAG에서는 질문을 넘기는 데 사용됩니다. 같은 클래스의 역할은 “입력 유지”이며, 내용이 무엇인지는 체인 구성이 정합니다.

RAG에 연결하려면 요약을 검색용 표현으로 추가하고 원문과 연결하는 작업이 별도로 필요합니다. 이 첨부 자체에 그 작업이 있다고 설명하면 안 됩니다.

## 8. 첨부 7: 텍스트·표·이미지 멀티모달 RAG

참고 코드: `references/attachment_7.py.txt`.

핵심 아이디어는 **요약 텍스트로 검색하되 실제 답변에는 원본 자료를 전달**하는 것입니다. 이미지 자체를 OpenAIEmbeddings에 넣는 예제가 아닙니다. 이미지 설명문을 텍스트 임베딩합니다.

### 8.1 PDF 요소 분리

`extract_pdf_elements(path, fname)`의 `partition_pdf`는 PDF를 텍스트·표·이미지 요소로 나누는 역할입니다. 이미지 추출과 표 구조 추론 옵션을 켜고 제목 중심 청킹을 설정합니다. 환경에 따라 OCR·PDF 도구·모델 다운로드가 추가로 필요합니다.

`categorize_elements`는 요소 타입 문자열을 보고 Table과 CompositeElement를 분류합니다. 다른 유형을 모두 자동 처리하는 코드는 아니므로 빠진 요소가 없는지 점검해야 합니다. 단순 `str(table)` 변환은 표의 구조 정보를 충분히 남기지 못할 수 있습니다.

`texts_4k_token`은 텍스트들을 합친 뒤 토큰 길이 기준 분할을 시도한 결과입니다. 이 코드는 CharacterTextSplitter를 사용하므로 긴 분리 불가능한 조각까지 반드시 4000토큰 이하라고 단정해서는 안 됩니다.

### 8.2 텍스트·표 요약

`generate_text_summaries`는 검색에 유리한 요약문을 만드는 프롬프트와 모델을 준비합니다. `.batch(..., {"max_concurrency": 5})`는 여러 항목을 최대 지정 동시성으로 처리합니다. 호출 횟수나 비용이 1회로 줄어드는 기능은 아닙니다.

`summarize_texts=False`이면 텍스트 원문을 검색 표현으로 그대로 사용합니다. 표는 별도 요약을 생성합니다. 반환되는 요약과 원본의 순서·개수 대응을 유지해야 이후 ID 연결이 맞습니다.

### 8.3 이미지 요약

`encode_image`는 이미지 바이트를 Base64 문자열로 바꿉니다. Base64는 전송 표현이지 압축이나 임베딩이 아닙니다. `image_summarize`는 텍스트 지시와 `image_url` 형태의 이미지 데이터를 시각 입력 가능한 모델에 보내 설명문을 받습니다.

`generate_img_summaries`는 폴더의 `.jpg` 파일을 정렬해 읽고 `img_base64_list`와 `image_summaries`를 같은 순서로 만듭니다. 다른 확장자의 이미지는 이 조건에서 제외됩니다.

### 8.4 요약과 원본 연결

`create_multi_vector_retriever`는 두 저장 계층을 사용합니다.

| 계층 | 저장되는 것 | 쓰임 |
| --- | --- | --- |
| vectorstore | 요약문과 `doc_id` | 질문과 가까운 요약 검색 |
| docstore | `doc_id`에 연결된 원본 텍스트/표/Base64 이미지 | 검색된 ID로 원본 반환 |

내부 `add_documents`는 UUID를 만들고, 요약 Document의 metadata에 같은 ID를 붙이고, 원본을 `docstore.mset`으로 저장합니다. `MultiVectorRetriever`는 검색된 요약의 ID를 사용해 원본을 돌려줍니다. 이 예제는 각 원본당 주로 한 요약을 넣지만 한 원본에 여러 검색 표현을 연결하는 구조로 확장할 수 있습니다.

### 8.5 검색 결과를 모델 입력으로 만들기

| 함수 | 역할 |
| --- | --- |
| `plt_img_base64` | 노트북에서 Base64 이미지를 표시 |
| `looks_like_base64` | 문자열 모양이 Base64 후보인지 검사 |
| `is_image_data` | 디코딩한 바이트 헤더로 이미지 후보 판별 |
| `resize_base64_image` | 이미지 크기 변경 후 다시 Base64로 인코딩 |
| `split_image_text_types` | 검색된 원본들을 이미지 목록과 텍스트 목록으로 분류 |
| `img_prompt_func` | 텍스트와 이미지가 포함된 HumanMessage 구성 |
| `multi_modal_rag_chain` | 검색→분류→메시지 생성→시각 모델→문자열 연결 |

`RunnableLambda`는 일반 Python 함수를 체인의 실행 단계로 감쌉니다. `split_image_text_types`는 Document가 들어오면 먼저 page_content를 꺼내고 이미지인지 판별합니다. `img_prompt_func`는 텍스트 템플릿 하나에 이미지 문자열을 넣는 대신, 이미지 블록과 텍스트 블록이 있는 멀티모달 메시지를 만듭니다.

### 8.6 이 코드에서 구분해서 볼 점

- `retriever.invoke(query, limit=6)`가 반드시 6개 검색을 설정한다고 가정하면 안 됩니다. 일반적인 vectorstore 검색 개수는 retriever의 `search_kwargs={"k": 6}`로 지정합니다. 원본 ID 중복 제거 후 반환 개수는 더 적을 수 있습니다.
- Base64 형태만 검사하면 일반 문자열도 후보가 될 수 있습니다. 헤더 검사도 완전한 이미지 검증기는 아닙니다. RIFF 헤더만으로 WebP를 확정하는 방식은 충분하지 않습니다.
- 크기를 `(1300, 600)`으로 고정하면 원본 비율이 달라지고 작은 글자가 읽히지 않을 수 있습니다. 차트는 해상도와 종횡비를 함께 고려해야 합니다.
- `resize_base64_image`는 원본 포맷으로 저장하지만 메시지 MIME은 항상 `image/jpeg`입니다. JPG가 아닌 이미지를 허용하려면 실제 포맷과 맞춰야 합니다.
- `docs[0]`이 이미지라는 보장이 없으므로 곧바로 `plt_img_base64(docs[0])`를 호출하는 시연 코드는 검색 결과 유형을 확인해야 합니다.
- `image_summaries[20]`은 21번째 요소입니다. 첨부의 “네 번째 요소” 주석은 코드와 다릅니다. 이미지가 21개 미만이면 IndexError가 납니다.
- 프롬프트에 투자 분석 역할이 들어 있는 것은 샘플 자료의 도메인 때문입니다. 스터디 자료용 앱에 그대로 복사할 이유는 없습니다.

이번 2주차 앱은 PDF에서도 **텍스트 추출만** 수행합니다. 이 멀티모달 파이프라인을 구현했다고 표시하지 않습니다.

## 9. 이번 프로젝트에서 원본을 어떻게 바꿨는가

| 원본의 구성 | 이번 구현 | 이유 |
| --- | --- | --- |
| 고정된 뉴스 URL/PDF 경로 | 내 파일·직접 입력·자체 위키 | 자체 문서 과제에 맞춤 |
| 노트북 전역 변수 | `RagBot`과 함수 입력 | 다른 셀의 문서 재사용 오류 방지 |
| Document 목록 그대로 context | `format_docs`로 근거 번호·본문 결합 | 프롬프트와 근거를 읽기 쉽게 만듦 |
| 질문을 실행해 문자열 출력 | Streamlit 채팅 화면 | 반복 질문·시연을 쉽게 함 |
| 고정 청킹 값 | 크기·겹침·k 조절 | 학습 목표인 전략 비교 지원 |
| 검색 결과 미표시 | 실제 LLM에 전달한 청크 표시 | 오류를 검색/생성 단계로 분리 |
| 키 없이는 실행 불가 | 명시적인 검색 데모 | 검색 흐름을 먼저 확인 |
| 환경·셀 실행 순서에 의존 | 가상환경·버전 목록·테스트 | 재현과 디버깅 지원 |

`RagBot`의 흐름은 `load_document` → `split_documents` → 임베딩 선택 → `FAISS.from_documents` → `as_retriever` → `retrieval_chain.invoke` → `build_answer_chain`입니다. 기본 예제의 단계 번호를 `rag.py` 주석에 남겼습니다.

## 10. 발표에서 설명할 수 있어야 하는 질문

1. 왜 문서를 나누나요? 전체 문서를 매번 보내는 대신 질문과 관련된 부분을 선택하기 위해서입니다. 경계에서 의미가 끊기는 문제도 함께 고려합니다.
2. 임베딩과 LLM은 어떻게 다른가요? 임베딩은 검색용 숫자 표현을 만들고 LLM은 선택된 근거를 읽어 답변을 생성합니다.
3. FAISS가 정답을 작성하나요? 아닙니다. 가까운 벡터와 연결된 문서를 찾습니다.
4. RAG는 모델을 학습시키나요? 이 프로젝트에서는 모델 가중치를 바꾸지 않습니다. 검색된 내용을 실행 시 프롬프트에 넣습니다.
5. 문서 밖 질문은 왜 어려운가요? top-k 검색은 답이 없어도 문서를 반환할 수 있고, 생성 모델이 빈 정보를 추측할 수 있기 때문입니다.
6. 채팅 화면이 있으면 대화를 기억하나요? 아닙니다. 과거 메시지를 모델 입력과 필요한 검색 질의에 반영하는 기능을 별도로 구현해야 합니다.
7. RAPTOR는 무엇을 추가하나요? 원문뿐 아니라 여러 추상화 수준의 요약도 검색 대상으로 추가합니다.
8. 멀티모달 예제는 무엇으로 이미지를 검색하나요? 이미지의 텍스트 요약을 임베딩해 검색하고 그 ID로 원본 이미지를 가져옵니다.
